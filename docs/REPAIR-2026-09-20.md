# Wallet, node switching, and widget repair

The reported failures had several connected causes:

- Node selection restarted the wallet service when its unit changed, closing the wallet and
  interrupting synchronization. It now applies the connection with `set_daemon` and leaves the
  wallet open. The pending-payment guards still apply.
- The bar checked the public node only while its panel was open, and the TUI checked it only
  on the Node screen. Both now use the shared, throttled background check. Concurrent pollers
  cannot start competing automatic checks, and partial responses are not consumed prematurely.
- An eight-second widget watchdog could kill a status command that was still making sequential,
  individually bounded wallet reads. The poll now bounds each operation to two seconds and
  allows sixty seconds for the complete sequence.
- The TUI used short read deadlines after opening/creating a wallet, unlike the CLI. Both now
  allow the refresh budget for those reads.
- A read timeout looked like a closed wallet; a confirmed closed wallet was labelled “catching
  up”; height zero hid initial progress. Busy, closed, and syncing states now differ.
- Transaction preparation checked local-node synchronization but not the wallet's height.
  A wallet still catching up now gets an explicit refusal before transaction construction.
- History confirmation and unlock figures used the height from their initial load. Their clock
  now advances with status observations.

The follow-up audit found and repaired these additional defects:

- Creating a wallet reopened the wallet immediately after Monero had already created and opened
  it. Creation now installs the daemon and records the session without a second open. Owned
  password buffers are also cleared on early errors, including failed service startup.
- Node changes saved the new selection before service installation or wallet acceptance. A
  cancelled change or failed installation now leaves the selection alone; a definite wallet
  rejection also restores the previous service rendering. A transport failure has an unknown
  outcome, so the desired selection remains saved and the error offers a retry. The picker and
  local-node action allow confirming the current target again.
- Late wallet/status/history reads could overwrite data from a newer wallet or configuration.
  Reads now carry a generation, and history requests have a sequence number. Old results cannot
  replace current addresses or history, clear a newer request's busy flag, or rewind confirmation
  counts after a newer status observation.
- The first repair's broader background polling exposed a regression when settings failed to
  load: checks could continue against the old configuration. Invalid settings now pause polling
  and new actions until repaired. Reload detection includes inode and size as well as modification
  time, so an atomic save sharing a timestamp is still noticed.

## Startup timeout and verification

The owner's subsequent 30-second wallet-open timeout exposed an authenticated cold-start bug.
The service journal showed startup at 09:20:46 and shutdown at 09:21:16. Wallet clients captured
the RPC login before service startup, but Monero generates a new login when it starts. The same
client then rejected every startup probe, timed out, and stopped the service. Context-backed
wallet clients now read the current login for each operation, retaining the bounded Digest retry
and never falling back to an old credential when the file is missing or invalid. Startup timeout
cleanup also leaves an already-running service alone instead of stopping someone else's session.

The previous offline integration check disabled authentication and missed this defect. It now
launches the app before the real wallet service, checks authenticated creation from cold, stops
the disposable service, and reopens its wallet after login rotation. All paths remain isolated.

## Widget redesign

The widget now follows the torrent panel's compact header: wallet picker, TUI, refresh, and
power. Opening a wallet shows existing wallet names and a masked password field inside the
widget. Power saves and stops the wallet service, closes the popup, and leaves the bar icon
available to reopen a wallet. Close wallet leaves the service running; the local node has its
own control. Advanced operations remain in the TUI.

The password uses a bounded standard-input pipe, never an argument or temporary file. The
field clears on submission and dismissal. Failed-open errors persist across successful polls,
and old status responses cannot overwrite state after an action. Open/create/close/stop all
respect the payment lock and unresolved-payment guard. A real offscreen Quickshell run covered
list, failed password, persistent error, retry, close, and stop. A separate rendered-panel check
confirmed that navigation/power shortcut letters reach the password field and Escape clears it.
The rendering used the installed Omarchy controls with only its Wayland panel window replaced
by an offscreen Window adapter. The actual desktop widget subsequently loaded successfully.

The test suite now models absent systemd services explicitly rather than inheriting the owner's
running services. Its final check compares the owner's service states and process IDs before
and after the run. The doctor idle-machine case also supplies its own empty process/port view.

Final checks after the redesign: the 369-test workspace and repository checks passed;
`tests/e2e.sh` passed 604 checks with three existing skips, and the live widget check passed 87.
Generated command documentation matches the binary. The final installed binary matches the
release build by SHA-256.
